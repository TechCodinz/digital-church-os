# Phase 11 Release Verification

This document records the reproducible release gates for the Phase 11 ministry experience and tenant-safe church operating system work.

## Automated production verification

The `Production Verification` workflow must pass on the exact branch head before this pull request can be marked ready for review.

The workflow verifies:

- dependency installation with development verification tooling available
- Prisma client generation
- Prisma schema validation
- migration deployment against a fresh PostgreSQL 16 database
- the committed historical Prisma core baseline plus every later migration
- lint
- optimized Next.js production build
- runtime smoke tests against the built production server and the freshly migrated database

## Phase 11 runtime assertions

The authenticated runtime smoke suite verifies the following behavior with deterministic test identities and two isolated church tenants:

### Public and guest behavior

- homepage is publicly reachable
- Live Service is publicly reachable without requiring a member login
- conference directory is publicly reachable
- public Live Service configuration exposes only allowlisted non-secret fields
- public church conference discovery includes public churches and excludes private churches
- public conference calendars are readable by guests
- private conference calendars are denied to guests
- conference mutations require authentication
- private Journey, Service Response, and Admin Settings routes redirect unauthenticated visitors to authentication

### Member privacy and spiritual formation

- credential sign-in succeeds for the seeded member account
- Journey and Daily Guide are accessible after authentication
- Journey API contains no `spiritualScore`
- Journey explicitly reports `spiritualScoring: false`
- private Journey continuity can be saved to the signed-in account
- the legacy global Live Service chat remains disabled with `410 TENANT_BROADCAST_SCOPE_REQUIRED`

### Church tenant isolation

- a STAFF member sees only the church where they hold active membership
- STAFF can activate that church workspace
- STAFF can write and read an operational record in that church
- the same STAFF member cannot read a different private church calendar
- STAFF can create a conference for their church
- STAFF cannot delete a conference when deletion requires OWNER or ADMIN
- a VIEWER can access the private church where they are a member
- VIEWER cannot write operational records
- VIEWER cannot create conferences

### Product admin and safe configuration

- CHURCH_ADMIN can access Admin Settings
- safe non-secret settings can be persisted
- provider credential fields are not returned by the settings API
- Live Service public configuration resolves persisted safe settings
- credential-bearing public URLs are rejected
- a church OWNER can perform an authorized tenant conference deletion

## Database reproducibility

The repository now contains:

`prisma/migrations/20260518000000_prisma_core_baseline/migration.sql`

This baseline was generated by Prisma from the repository's historical schema immediately before the first feature migration. It restores the missing foundational schema that earlier migrations assumed already existed. A blank PostgreSQL database must be able to apply this baseline and every subsequent migration successfully.

## Deployment truthfulness

A successful Vercel build does not by itself prove authenticated preview behavior. Preview deployments also require correctly configured runtime environment variables, including a production-strength NextAuth secret and database connectivity, before manual member testing is representative.

Do not expose provider credentials in public configuration or generic audit logs. Do not re-enable the legacy global Live Service chat until a church/broadcast-room-scoped authorization model exists.

## Merge gate

Keep PR #2 draft until:

1. exact-head Production Verification is green;
2. the exact head has a READY Vercel preview;
3. required preview/staging environment variables and database are configured;
4. manual desktop/mobile smoke testing is completed against the deployed preview;
5. remaining security/dependency review is completed or explicitly dispositioned;
6. the final tenant, invitation, conference, privacy, and ministry experience checks are accepted.
